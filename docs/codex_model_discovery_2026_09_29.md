# Codex model discovery in an open Switchy window

## Finding

The Worldbuilding Codex window is using a model catalog loaded before `gpt-6-sol` was added. Its WSL config selects `model_catalog_json = "context_models.json"`; [Codex's config reference](https://learn.chatgpt.com/docs/config-file/config-reference) says this file is loaded at startup. The installed Codex 0.159.0 binary already bundled Sol, but the custom catalog had nine entries and omitted it. Both Windows and WSL custom catalogs now contain the exact bundled Sol profile, with their other nine entries unchanged. This fixes discovery for new servers, not the already running Worldbuilding server.

Switchy contributes to the stale window's lifetime: its [Codex shell function](../src-tauri/src/proxy/codex_engine.rs) starts one app-server per interactive WSL window and keeps the remote client attached to it. On account changes, Switchy sends `account/login/start` to that server; its two-second loop does not reload the catalog or replace the server. Switchy's [proxy takeover](../src-tauri/src/services/proxy.rs) edits `openai_base_url` while preserving the catalog setting, and its [Codex backend GET handler](../src-tauri/src/proxy/handlers.rs) forwards model requests upstream without a model-list cache. The `models_cache.json` read in [keep-warm](../src-tauri/src/proxy/keep_warm.rs) selects a warm-up request model; it does not serve `model/list` or control worker spawning.

## Owner and refresh path

Codex owns the catalog and its startup loading. Switchy owns the per-window app-server lifecycle it adds. When a stale window's Codex exits with a refresh queued, its shell starts a new server from the installed CLI and resumes the window's conversation on it with the current catalog. The window's old server keeps every conversation the window opened loaded until it stops; while the refresh is queued, Switchy names the one conversation with a message among them (leaving out the empty thread a window starts with, the short-lived thread that titles a conversation, and subagents' threads) in `<window>.thread` beside the session file, and the shell runs `codex resume <id>`. With none or several, the shell opens the conversation picker. Other sessions and servers continue running. [Codex's app-server documentation](https://learn.chatgpt.com/docs/app-server) documents `thread/resume`, which preserves conversation history across server processes. An in-flight turn cannot continue uninterrupted through server replacement.

Switchy detects when an open Windows PowerShell or WSL window's server predates its installed CLI or selected catalog and lists its terminal in Pool settings. **Refresh** (or `refresh_codex_terminal` over `POST /switchy/invoke`) queues the refresh and, once no turn is running on the window's server, Switchy ends that Codex itself; it never ends one mid-turn. The shell records at launch where Codex runs (`terminal=` in the session file). In an Orca pane (the shell has `ORCA_PANE_KEY`; WSL shells Orca starts have it too) Switchy finds the pane's handle with `orca terminal list --json`, sends Ctrl+C to clear unsent input, then `/exit` and Enter as separate plain inputs, so Codex quits as a user would. `orca terminal send --text … --enter` is not used: Orca treats that as an agent prompt and watches for its submission; sent right after a reply ended, the call had not returned 10 s later, and the restarted Codex quit as well, leaving the terminal at its shell prompt. Plain input returns at once and is typed once. In any other terminal it ends the client process found by its `--remote` address (on Windows its process tree; in WSL SIGTERM, then SIGKILL), first writing `ended` into the refresh marker; the shell then restores the console modes or `stty` state it saved before launching Codex and leaves the alternate screen, since a client ended from outside cannot. If Codex is still open 15 s after `/exit`, Switchy ends its client the same way. Stopping only the window's server does not end the client: it waits on "Reconnecting to server…" indefinitely. For a window whose shell predates the `terminal=` record, Switchy reads the Orca variables from its client process's environment (in WSL `/proc/<pid>/environ`; on Windows the environment block named in the process's PEB), which the shell passed down. Found in an Orca pane, it gets **Refresh** and is quit by typing `/exit` only, never ended from outside, since that shell cannot restore the terminal; a shell older than 1.0.38 then opens the conversation picker instead of resuming. Elsewhere it keeps refresh on exit, which waits for the user to exit Codex. Account switches sign the existing server in to the selected account; they do not reload its startup catalog.
